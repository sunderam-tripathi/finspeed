# Plan — WEB-035

## Context

The current Build Your Ride route is a two-frame demonstration with global component choices. Finspeed actually has a deliberately small but varied range of eleven named models and up to eighteen catalogued physical SKUs. A premium configurator must therefore begin with product truth: model, wheel and frame variants, included equipment, compatible choices, honest pricing, and a visual state that remains mechanically and visually faithful to the selected bicycle.

## Goals

- Model all eleven product families and catalogued physical SKUs in one versioned configuration contract.
- Replace the five-tab demo with a responsive seven-stage journey: ride type, bicycle, fit/wheels, setup, finish, add-ons, and review.
- Evaluate compatibility whenever the model or fit changes, remove invalid selections explicitly, and never expose an unverified combination as purchasable.
- Update the preview, specification summary, price, persistence, cart identity, and review state from the same resolved configuration.
- Establish a reproducible, provenance-backed visual asset contract for future component-level image generation.
- Preserve the existing editorial design language, shared header geometry, light/dark themes, routes, and commerce behavior.

## Risks

- The storefront data, distributor PDF, and older frozen CSV disagree on some names, prices, and specifications; conflicts must remain provisional or disabled.
- Product photography can drift in scale, crop, decals, or component geometry if generated without a canonical canvas and identity checks.
- Persisted v1 builds can point at removed or incompatible choices after migration.
- A desktop-only studio can become unusable on tablet and mobile if the image stage, progress rail, and actions compete for viewport height.
- Configuration fingerprints that omit fit, components, finish, or accessories can merge distinct cart lines.

## Steps

1. Freeze the provisional authority matrix for all models and SKUs, recording source and validation status for every selectable fact.
2. Implement versioned configuration data, compatibility resolution, pricing, migration, visual resolution, and deterministic cart fingerprints.
3. Rebuild Build Your Ride as the seven-stage accessible journey using the existing editorial tokens and verified product masters.
4. Establish the canonical configurator asset manifest and integrate the first catalog-accurate visual variant pilot.
5. Validate compatibility enumeration, persisted-state migration, desktop/tablet/mobile layout, theme parity, keyboard behavior, cart handoff, and production build.
6. Record proof, telemetry, and any remaining asset-generation backlog without overstating unverified product availability.

## 2026-07-21 exhaustive configurator production contract

- The public seven-stage wizard exposes eleven products, fourteen distinct fit/wheel states, two brake systems, two fork setups, two drivetrains, five finishes, and two add-on states. Exhaustive enumeration therefore contains 1,120 unique selectable build states.
- Every build state must resolve in both light and dark themes and at 480, 960, and 1600 pixel source widths. The governed delivery contract is therefore 2,240 themed states and 6,720 responsive WebP assets.
- The visual pipeline uses 224 product-accurate hardware masters as the controlled source layer. Thirty-three masters were already governed when the exhaustive pass began; 191 missing masters entered the production queue.
- Runtime activation is fail-closed. `configurator-matrix-availability.js` lists only product matrices whose complete inventory and generation record have passed registration. An unfinished product cannot resolve to a missing or partly generated matrix.
- Each product matrix includes fit/wheel identity where applicable, component state, finish, add-on state, theme, and responsive width. Manifest registration binds every completed matrix back to its exact catalog SKU set and selection-dependent visual classes.
- AI editing begins from a flattened clean-white copy of the exact canonical product cutout. Transparent-input generations were rejected after visible geometry and paint drift; rejected outputs are retained only as proof and never enter the delivery inventory.
- Every accepted master must pass automated alpha, resolution, clipping, silhouette, catalog-paint overlap, and paint-area checks. Product wordmark, component accuracy, angle, scale, and visual coherence remain subject to human contact-sheet review before registration.
- The first complete non-Mako production target is Shark Blue. Remaining products will be processed through the same master audit, matrix build, contact-sheet review, manifest registration, resolver test, and responsive/theme QA gates.
- This work is local only. No deployment is permitted until the user explicitly requests it.
