# Plan — WEB-034

## Context

Finspeed has a deliberately small range, so the previous catalogue-card storefront made the product feel more ordinary and more crowded than it is. The selected warm-light Editorial Navigation Index and Bespoke Ride Studio sources establish the replacement: porcelain surfaces, technical cyan accents, a mono/display/body type hierarchy, large product studies, and four high-intent journeys rather than permanent category tabs.

The implementation must now be consistent end to end. A convincing menu or configurator is not sufficient if product detail, cart, checkout, owners, support, search, account, or legacy URLs fall back to the old shell or expose non-working actions.

## Goals

- Apply one tokenised warm premium editorial system to every customer storefront route.
- Organise primary navigation around The Bikes, Build Your Ride, Our Engineering, and Visit Finspeed.
- Present the small range as a curated edit rather than a dense product-card catalogue.
- Preserve verified product imagery, prices, specifications, dealer locations, warranty terms, and support channels.
- Keep configuration, cart, checkout, search, account, newsletter, and support actions functional and honest.
- Preserve legacy public URLs while rendering them through the new shared shell.
- Verify desktop and mobile fidelity against the supplied sources before release.

## Risks

- Opaque product photography can reveal a rectangular background against the porcelain canvas; menu and configurator assets must be verified at pixel level.
- A full-screen menu or cart drawer can trap focus or leave the background interactive.
- Configured line items can lose unit price or selected components when quantity changes, during checkout, or in order history.
- Legacy Next.js route files can bypass the shared React-router shell.
- Forms without a configured endpoint must never pretend that a request was submitted.

## Steps

1. Inventory the supplied references, existing storefront routes, product masters, governed owner/support claims, and active scenario contracts.
2. Establish the porcelain editorial design tokens and shared header, menu, footer, responsive, focus, and theme foundations.
3. Implement the curated home/range, bespoke build, engineering, product, cart, checkout, account, authentication, support, owner, and legacy public journeys without removing contracted behavior.
4. Verify configuration and customer data from selection through cart, checkout, order history, delivery details, and owner support.
5. Compare representative desktop and mobile states with the supplied references; remediate imagery, blending, overflow, focus, keyboard, contrast, and console defects.
6. Run the governed plan, parity, lint, unit, focused, accessibility, full-regression, production-build, slice, telemetry, and diff gates; archive current proof.
7. Commit the exact verified release, deploy it through the configured production integrations, and repeat runtime symptom checks on both the public domain and Amplify origin.
